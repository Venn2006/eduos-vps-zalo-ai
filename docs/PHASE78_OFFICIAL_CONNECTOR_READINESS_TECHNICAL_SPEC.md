# Phase 78: Official Connector Readiness Technical Spec

## 1. Executive summary
EduOS currently relies exclusively on deterministic mock/demo data for all its modules. Real connectors are designated for future work.
To ensure the long-term safety, legality, and stability of the platform, the official connector architecture mandates strict adherence to the following principles:
- Connectors must utilize **official API paths** only.
- All connections require explicit, documented **tenant consent**.
- All outbound actions are heavily governed by **audit logs** and **human approval**.
- **Personal Zalo scraping, browser automation logins, and stealth monitoring are strictly prohibited**.

## 3. Zalo connector policy
EduOS must interact with the Zalo ecosystem strictly through official channels.
**Allowed:**
- Zalo Official Account (OA) business channel integration.
- Connecting to a customer-owned, verified official account.
- Integration based on explicit tenant opt-in.
- Using approved Zalo message templates (ZNS).
- Staff handoff workflow mapping to EduOS roles.
- Draft-only modes where EduOS creates the message, but a human must click send on Zalo (initially).

**Not Allowed:**
- Personal Zalo scraping or using unofficial API wrappers.
- Collecting or storing staff personal Zalo credentials.
- Browser automation (e.g., Puppeteer/Selenium) to log into Zalo Web.
- Stealth monitoring of employee communications.
- Private inbox scraping.
- Bypassing Zalo's rate limits or platform rules.
- Real autonomous sending before the approval system is thoroughly vetted.

## 4. Meta/Facebook connector policy
**Policy:**
- Connections must use official Page/Business Manager access.
- Webhooks must only be enabled after successfully passing the Meta App Review process.
- Explicit tenant-owned page consent is mandatory via Facebook Login for Business.
- No personal user account scraping or monitoring.
- No unapproved outbound automation (chatbot flows must be transparent).
- Must enforce a draft-and-approval workflow before transitioning to fully automated replies.

## 5. Banking/payment connector policy
**Policy:**
- Integrations (e.g., VietQR, Open Banking APIs) must be strictly **read-only** for reconciliation purposes.
- EduOS will perform **no money movement**.
- EduOS will perform **no payment mutation** or initiation.
- EduOS will **not store sensitive banking credentials** (passwords, OTPs) in the application database.
- Explicit, signed tenant consent is required before linking a bank account.
- Comprehensive audit logs must record every reconciliation event.
- Manual review by a user with the `Finance` role is required to finalize reconciliations.

## 6. AI/LLM connector policy
**Policy:**
- Live LLM calls are currently OFF.
- Future live LLM integrations must operate on **redacted context** (PII removed before sending to the provider).
- Do not send full PII (phone numbers, full names, addresses) unless absolutely required for the specific prompt task.
- Outbound copy generated by the LLM strictly requires **human approval** before sending.
- Tenant opt-in is required to use AI features.
- Audit logs should capture prompt metadata (model, tokens, intent), not the full sensitive content unless explicitly configured by the tenant for compliance.
- **No autonomous send** capabilities until the sandbox pilot phase is successful.

## 7. Consent and tenant onboarding checklist
Before activating any live connector for a tenant, the following must be completed:
- [ ] Written tenant opt-in agreement signed.
- [ ] Data processing scope clearly defined in the contract.
- [ ] Proof of ownership for the channels (e.g., Zalo OA admin rights, Facebook Page admin rights).
- [ ] Admin role assignment explicitly configured in EduOS.
- [ ] Disclosure policy provided to staff regarding work-channel monitoring.
- [ ] Parent/student data privacy notice updated by the center.
- [ ] Data retention and deletion policy agreed upon.
- [ ] Pilot success metrics defined.
- [ ] Rollback plan documented in case of connector failure.

## 8. Data minimization and PII rules
- Phone numbers must be masked in the UI by default (e.g., `090****123`).
- Avoid exposing the full message history to the LLM; truncate or summarize past context.
- Implement a redaction layer before sending data to AI context windows.
- Store raw provider payloads only if necessary for debugging, and ensure they are encrypted and access-controlled.
- All access to unmasked PII must be recorded in the audit log.
- Enforce a strict data retention period (e.g., purge raw payloads after 30 days).

## 9. Outbox and approval architecture
Future safe architecture pipeline:
1. **Inbound Webhook** → Receive payload from provider.
2. **Normalization** → Standardize payload into internal EduOS format.
3. **Consent Check** → Verify tenant has an active, consented integration.
4. **Context Builder** → Fetch relevant CRM/Academic context.
5. **Policy Engine** → Run automation rules (e.g., does this need approval?).
6. **Draft/Outbox** → Stage the message in the `Outbox`.

- There is **no direct send** from the AI agent to the connector.
- Outbound messages require role-based approval (Admin, Teacher, Finance).
- The actual send worker remains disabled until pilot approval.
- Audit events are generated before staging and after sending.
- **Idempotency keys** must be used for all outbound connector requests to prevent duplicate sends.

## 10. Audit log requirements
Every critical action and connector event must log:
- `tenantId`
- `connectorType` (Zalo, Meta, Bank, LLM)
- `eventType` (Inbound, Outbound, Draft, Approve, Reject, Error)
- `sourceObjectId` (MessageID, TaskID, PaymentID)
- `payloadHash` (For integrity verification)
- `actorId` (System, Agent, or UserID)
- `role` (Role of the approver)
- `automationMode` (Copilot, Autopilot, Disabled)
- `approvalStatus`
- `redactionStatus`
- `outboxId`
- `timestamp`
- `errorCode`
- `retentionPolicy`

## 11. Feature flag requirements
The following feature flags govern connector access:
- `connector.zalo.enabled`
- `connector.meta.enabled`
- `connector.email.enabled`
- `connector.sms.enabled`
- `connector.bank.readOnly`
- `connector.llm.liveEnabled`
- `outbox.realSendEnabled`
- `approvals.required`
- `pii.redaction.enabled`

**Rules:**
- All real connector and send flags default **OFF**.
- Flags are evaluated on a **per-tenant** basis.
- Flag status must be visible and configurable only in the Safety Center by an Admin.

## 12. Pilot implementation sequence
1. **Docs-only readiness** (Current Phase)
2. **Manual import/manual review**: CSV based ingestion for safe testing.
3. **Read-only official connector pilot**: Listening to webhooks without sending capability.
4. **Draft-only AI suggestions**: AI reads inbound data and drafts responses in the UI.
5. **Human-approved outbox**: Staff clicks "Send" on the draft, triggering the real send worker.
6. **Limited real send pilot**: Highly constrained autopilot for specific scenarios (e.g., generic welcome messages).
7. **Post-pilot audit**: Review logs, errors, and safety metrics.

## 13. Technical open questions
- **Zalo APIs**: Which official Zalo OA APIs and permission scopes are available for our exact CRM use case?
- **Meta App Review**: What is the expected timeline and permission scope for the Meta App Review process?
- **SMS Compliance**: What are the specific compliance requirements for Vietnam SMS providers (Brandname registration)?
- **Bank Partner**: Which banking API aggregator (e.g., Casso, SeABank Open API) offers the most secure read-only webhook?
- **Encryption**: What key management system (KMS) will be used for storing tenant OAuth tokens?
- **Data Retention**: What is the legal requirement for data retention vs. the center's preference?
- **Audit Storage**: Should audit logs be moved to a cold storage solution (e.g., S3/ClickHouse) to prevent Postgres bloat?
- **Webhooks**: What is the retry and idempotency strategy for failed inbound webhooks?
- **Rate Limits**: How do we queue outbound messages to respect provider rate limits?
- **Secrets**: How will tenant-level API secrets be managed securely?
